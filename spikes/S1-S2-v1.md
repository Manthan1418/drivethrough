# Spike memo — S1 (Drive proxy throughput) + S2 (chunk PUT streaming)

**Date:** 2026-10-22 · **Plan:** Vercel Hobby (function region `sin1`) · **Gate:** P0.0 exit criterion (tech.md §12) — "spike memo in repo; go/no-go on §6 choices". **S5** was already closed earlier (cross-origin bearer auth verified live 2026-10-20).

**Verdict: S1 → GO on variant A (Vercel streamed function). S2 → GO on the spec'd raw `Content-Range` PUT at 4 MB chunks (no multipart, no Worker relay).** No §6 design change required; both §6 choices validated as written.

## Method

Throwaway route handlers deployed to **production** (Vercel Hobby, `sin1`), authed with a real Firebase bearer, telemetry carried in responses/headers (Vercel function logs are not accessible to the operator):

- `PUT /api/spike/s2?session=<resumable-URL>` — pass-through streaming: incoming chunk body → Google resumable session via `fetch({ body: req.body, duplex: 'half' })`, **zero buffering**; session URL allow-listed to `https://www.googleapis.com`; response returned RSS start/end, forward time, Drive's status.
- `GET /api/spike/s1?accountId=&id=` — streams `alt=media` from Drive (Range passthrough), zero buffering; response headers `x-spike-*` (upstream status, upstream TTFB, RSS); wall-clock MB/s measured client-side.

Test data: `/dev/urandom` payloads; a 32 MB file was built **through the S2 relay** (i.e. exactly the future upload architecture) and served as S1's download input. All test files created on the connected Drive were deleted afterwards; `drivethrough/` folder verified 0 files and free space verified restored to 138 MiB after each run.

Spike-only shortcuts (both routes deleted immediately after this memo): account lookup by `accountId` without ownership scoping; access token refreshed in-memory if near expiry. Acceptable because the routes existed for minutes, only two users exist, and they were removed in the follow-up commit.

## S2 results — chunk PUT through the function

| Test | Body | Result |
|---|---|---|
| A — single chunk | 8 MB | ❌ **HTTP 413 `FUNCTION_PAYLOAD_TOO_LARGE`** — rejected at the Vercel edge, before the function ran |
| C — single chunk | 16 MB | ❌ same 413 |
| X — multi-chunk | 32 MB as **8 × 4 MB** raw PUTs with `Content-Range` | ✅ all 8 relayed: Drive returned `308 ×7 → 200` + file metadata |

- Forward time per 4 MB chunk: **1.2–2.9 s** (includes client → Vercel `sin1` → Google double hop).
- Memory: RSS **93 → 129 MB** across the whole run, plateauing — **no buffering, `duplex:'half'` holds** under Vercel's body handling (the core S2 question: **yes**).
- Edge cap empirically confirmed at ~4.5 MB (R1 / limits row in tech.md §2): it is enforced *before* function invocation, so chunk size must stay under it by design, not by hope.

**Decision vs §7 S2 options:**
- ❌ multipart formData — **not needed**: raw binary PUT streams fine under the cap and avoids framing overhead. tech.md §6 upload row already mandates raw `Content-Range` PUT (NOT multipart) — **validated as written; chunk size locked at 4 MB**.
- ❌ Worker relay for 16–32 MB chunks — **not adopted** (fewer requests not worth an extra hop; 4 MB × free-tier request budgets are ample). Remains a P1 option if request volume ever becomes a problem.
- ⏸ direct-to-Drive from the browser — unchanged, stays **P2-3**.

## S1 results — Drive proxy throughput × maxDuration

32 MB random file; four proxy downloads + two direct-from-Google baseline downloads on the same machine/network:

| Path | Cold | Warm |
|---|---|---|
| **Proxy via Vercel `sin1`** (variant A) | 1.86 / 1.75 MB/s | 1.71 / 2.18 MB/s |
| **Direct from Google** (no Vercel — baseline) | 1.33 MB/s | 4.24 MB/s |

- **The proxy is not the bottleneck**: proxy ≈ direct on the same client; the binding constraint is the client's own link (~1.3–4.2 MB/s to *any* host), not Vercel.
- Range probe: `Range: bytes=0-1048575` → **206**, exact `content-range: bytes 0-1048575/33554432` — windowed/range downloading validated.
- Upstream TTFB 471–630 ms; RSS 98 → 158 MB over the run; 32 MB ≈ 15–18 s wall — `maxDuration: 300` never approached (a 16 MB window at the worst observed 1.33 MB/s ≈ 12 s, huge headroom).
- Multi-GB files are impossible in one window on Hobby (~400 MB ceiling at 1.33 MB/s even if duration weren't a concern) → the spec'd size guard `FILE_TOO_LARGE_FOR_PLAN` + range downloader remains correct.

**Decision vs §7 S1 options:**
- ✅ **variant A (Vercel streamed function) adopted for v1**, with the spec'd ≤ 16 MB response windows + browser range downloader — throughput is comparable to direct-from-Drive; Vercel is not the limiter.
- ❌ variant B (free Cloudflare Worker relay) — **not adopted**; stays documented contingency per §6 if a fast-link deployment ever shows Vercel-bound throughput, or if egress budget pressure appears.
- ⏸ temporary public reader link — unchanged: last-resort opt-in.
- **Egress budget watch item:** Hobby ≈ 100 GB/mo ≈ 14 h of sustained 2 MB/s download across all users; windowed downloads keep usage predictable, and the Worker relay is the free upgrade path if it ever tightens.

**Caveats:** single client (India, 1–4.2 MB/s link), single region (`sin1`), n = 2–4 per condition. Re-measure if a fast-link scenario (different continent / datacenter client) appears; the decision rule in §7 (Worker only if Vercel is the limiter) is what to re-run.

## Platform gotchas recorded during the spike

- Next.js App Router **excludes `_`-prefixed folders from routing** — the routes were initially `_spike/` (404) and had to be renamed `spike/`.
- Vercel request-body cap `FUNCTION_PAYLOAD_TOO_LARGE` (413) fires at the edge for bodies > ~4.5 MB, even on routes that never intend to buffer.
- Resumable session URLs accept `PUT` only (a `GET` to read the resulting file id returns 405) — capture the id from the final `PUT`'s 200 response instead.
- Telemetry-in-response/headers works well for black-box diagnosis when function logs are inaccessible.
